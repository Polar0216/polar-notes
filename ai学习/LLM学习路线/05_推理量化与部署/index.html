    模块 5：推理、量化与本地部署¶

    目标¶

    从 logits 自己实现 greedy、temperature、top-k、top-p 和 beam search；理解 KV Cache、prefill/decode、量化及服务指标，部署一个本地可调用 API。

    Temperature 概率比、Top-k/Top-p 手算、KV Cache 大小和量化误差推导见 采样、KV Cache 与量化推导。

    学习导航¶

    先理解生成与采样，再用补充讲义核对公式和缓存大小；随后实现最小 API、完成验收与复盘，最后再做文末 Project 的性能对比。

    1. 生成循环¶

    @torch.no_grad()
def generate(model, idx, max_new_tokens, temperature=1.0):
    model.eval()
    for _ in range(max_new_tokens):
        idx_cond = idx[:, -model.cfg.block_size:]
        logits, _ = model(idx_cond)
        next_logits = logits[:, -1, :] / temperature
        probs = torch.softmax(next_logits, dim=-1)
        next_id = torch.multinomial(probs, num_samples=1)
        idx = torch.cat([idx, next_id], dim=1)
    return idx

    生成应处理 EOS、最大长度、随机种子、停止字符串、重复和非法参数。截断到 block_size 是绝对位置模型的简单办法，但会丢掉早期上下文。

    2. Temperature¶

    $ p_i=softmax(z_i/T) $

    • T<1：分布更尖锐，更确定。
    • T>1：分布更平，更随机。
    • T→0 不应直接做除法，通常转为 greedy。

    Temperature 不会让模型“知道更多”，只改变采样分布。

    3. Top-k 与 Top-p¶

    Top-k 只保留概率最高的 k 个 token，其余设为负无穷再 Softmax。固定 k 不管分布本来很尖还是很平。

    Top-p（nucleus）把 token 按概率降序，保留累计概率达到 p 的最小集合。因此候选数量会随上下文改变。

    实现顺序通常是处理 logits、过滤、再归一化采样。必须保证至少留一个 token。

    def top_k_filter(logits, k):
    if k is None or k <= 0:
        return logits
    k = min(k, logits.size(-1))
    threshold = torch.topk(logits, k).values[..., -1, None]
    return logits.masked_fill(logits < threshold, float("-inf"))

    4. Beam Search¶

    Beam Search 每步保留累计对数概率最高的若干序列，适合答案较确定的任务。直接累加 log probability 会偏爱短序列，常用长度惩罚。开放式聊天里 beam 往往产生安全但平淡/重复的文本，不一定优于采样。

    实现要维护：序列、累计分数、是否结束、每个 beam 对应的 KV cache，并避免已经 EOS 的 beam 继续扩展。

    5. KV Cache 为什么加速¶

    不缓存时，第 t 步会重新为前面所有 token 计算 K/V，重复工作。每层缓存历史 K/V，新一步只计算新 token 的 Q/K/V，再让新 Q 与历史 K 交互。

    prefill：一次处理整个 prompt，建立各层 KV cache
decode ：每步输入一个新 token，读取并扩展 cache

    缓存不改变理论输出（在相同数值精度和实现下），只是用内存换计算。缓存大小大致随：层数 × batch × KV heads × 序列长度 × head dim × K/V 两份 × 每元素字节增长。长上下文并不免费。

    MHA、MQA、GQA¶

    • MHA：每个 query head 有自己的 K/V。
    • MQA：所有 query heads 共享一组 K/V，cache 小。
    • GQA：若干 query heads 共享一组 K/V，在质量和效率间折中。

    6. 量化¶

    量化用更少位数表示权重或激活：FP32、FP16/BF16、INT8、INT4 等。它减少存储和带宽，有时提高速度，但速度取决于硬件和内核支持。

    基本思想：把浮点范围映射到离散整数。

    $ q=round(x/s)+z,\quad \hat{x}=s(q-z) $

    s 是 scale，z 是 zero point。per-tensor 共用一套参数，per-channel/group 更精细但元数据和计算更复杂。

    • PTQ：训练后量化，便宜。
    • QAT：训练中模拟量化误差，通常精度更好但成本高。
    • weight-only：只量化权重。
    • 动态/静态量化：激活 scale 在运行时或校准后确定。

    “4bit 模型占用=参数量×0.5 字节”只是下限估算，还要加 scale、未量化层、KV cache、运行时 workspace。

    7. 推理引擎读什么¶

    • llama.cpp：CPU/消费级硬件、本地量化格式和高效内核。
    • vLLM：服务吞吐、连续 batching、KV cache 管理。
    • SGLang：结构化生成和高性能服务/运行时思路。

    先理解接口与 benchmark，再读调度器、cache manager、kernel。不要试图从第一天读完整个引擎。

    8. 服务指标¶

    • TTFT：time to first token，首 token 延迟，受 prefill 影响。
    • TPOT：time per output token，后续 token 间延迟。
    • 吞吐：每秒生成 token/完成请求数。
    • 并发：同时请求数。
    • P50/P95/P99：延迟分位数，平均值会掩盖长尾。

    Benchmark 必须固定模型、输入/输出长度分布、并发、硬件、精度和采样设置。只报“tokens/s”而不报这些条件没有意义。

    9. 本地 API 的最小设计¶

    建议先做：

    POST /generate
请求：prompt、max_new_tokens、temperature、top_p、seed
响应：text、input_tokens、output_tokens、latency_ms、finish_reason

    加上参数上限、超时、并发限制、日志脱敏和健康检查。不要把服务默认监听到公网；本地开发绑定回环地址。

    10. 常见误区¶

    • 把 temperature 设为 0 后仍除以 0。
    • 在概率上 top-k 后忘记重新归一化。
    • cache 的 batch/head/sequence 维顺序错位。
    • 把量化模型的体积减少等同于任何硬件上都加速。
    • 用不同输入长度比较两个引擎。
    • 把生成文本解码后再截停止词，却继续浪费大量生成。

    验收与复盘¶

    • 能解释每种采样方法的适用场景和失败模式。
    • KV cache 前后 greedy token 序列一致（允许极小数值差异，但结果应测试）。
    • benchmark 报告包含硬件、精度、输入输出长度和分位延迟。
    • 本地 API 有参数校验、超时和非公网默认配置。
