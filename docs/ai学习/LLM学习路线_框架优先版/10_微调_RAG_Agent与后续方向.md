# 第三遍之三：微调、RAG、Agent 与后续方向

本章把已经掌握的基础语言模型放入完整应用栈，区分参数学习、外部知识检索、工具执行和状态管理。目标是建立决策框架，而不是把所有能力都误认为“继续训练模型”。

## 1. LLM 系统的分层结构

```text
用户与应用界面
  ↓
任务编排与 Agent 状态
  ↓
工具、RAG、Memory 与安全策略
  ↓
Prompt / Context 构造
  ↓
基础模型或微调模型
  ↓
推理引擎与硬件
```

底层 GPT 仍执行“上下文 → 下一个 token 概率”。上层系统通过提供上下文、调用外部能力、保存状态和验证结果扩展其用途。

## 2. 预训练与微调的职责差异

| 方法 | 数据形式 | 主要目标 |
|---|---|---|
| 预训练 | 大规模连续文本 | 学习通用语言统计与表示 |
| SFT | 指令—回答或消息序列 | 学习任务格式、行为和风格 |
| 偏好优化 | 偏好对、奖励或反馈 | 使输出更符合人类偏好或策略 |
| 继续预训练 | 特定领域连续文本 | 适应领域语言与知识分布 |

微调不会自动保证事实正确、安全或不遗忘。必须先明确目标、基线和评估集。

## 3. SFT 的标签与损失范围

对一条指令数据：

```text
用户：解释梯度下降
助手：梯度下降是一种……
```

训练输入可能包含完整对话，但通常只让助手回答部分参与 loss：

```text
系统提示与用户部分：label = -100，不计算损失
助手回答部分：label = 对应下一个 token
```

具体模板、特殊 token 和 Mask 必须与目标模型 Tokenizer 一致。错误模板会让模型学习无意义边界或把用户文本也当成需要复述的答案。

## 4. LoRA 与 QLoRA 的参数高效训练

LoRA 冻结原权重 $W$，学习低秩增量：

$$
W'=W+\Delta W,
\qquad
\Delta W=BA
$$

若原矩阵为 $d_{\text{out}}\times d_{\text{in}}$，秩 $r$ 很小：

$$
A\in\mathbb{R}^{r\times d_{\text{in}}},
\qquad
B\in\mathbb{R}^{d_{\text{out}}\times r}
$$

可训练参数从 $d_{\text{out}}d_{\text{in}}$ 降到：

$$
r(d_{\text{in}}+d_{\text{out}})
$$

QLoRA 进一步以低比特形式保存冻结的基础权重，同时用较高精度训练 LoRA 参数。它降低权重内存，但激活、梯度和优化器状态仍占资源。

## 5. RAG 提供可更新的外部知识

RAG 的典型流程：

```text
用户问题
→ 查询改写或规范化
→ Embedding
→ 向量或混合检索
→ 重排
→ 选择证据片段
→ 拼入 Prompt
→ LLM 生成带引用回答
→ 证据与答案评估
```

RAG 不改变基础模型参数，适合需要频繁更新、可追溯或私有的知识。

核心评估需要分层：

```text
检索层：相关证据是否被找到
上下文层：证据是否被正确截取和排序
生成层：回答是否由证据支持
端到端：用户任务是否解决
```

只看最终回答会混淆“没检索到”和“检索到了但模型没用好”。

## 6. Tool Calling 扩展可执行能力

语言模型负责提出结构化调用意图，宿主程序负责真正执行：

```text
用户请求
→ 模型选择工具并生成参数
→ 程序按 schema 校验参数
→ 权限与策略检查
→ 执行工具
→ 返回结构化结果
→ 模型组织最终回答
```

工具描述不是权限。即使模型产生合法 JSON，也必须由宿主程序限制可调用工具、参数范围、文件路径、网络目标与副作用。

高风险写操作需要确认、幂等设计、审计日志和失败恢复。

## 7. Agent 是受控的状态循环

最小 Agent 循环：

```text
读取目标和当前状态
→ 选择下一动作
→ 执行动作
→ 观察结果
→ 更新状态
→ 检查完成、失败或预算条件
→ 必要时继续
```

Agent 不等于“让模型无限思考”。可靠 Agent 需要：

- 明确目标与完成条件；
- 有限动作空间；
- 工具输入输出 schema；
- 步数、时间和费用预算；
- 可恢复状态；
- 权限边界与人工确认；
- 轨迹日志与可重复评估。

先实现可观察的单 Agent，再判断多 Agent 是否真正提高结果。

## 8. Memory 的不同时间尺度

| 类型 | 保存内容 | 常见载体 |
|---|---|---|
| 工作记忆 | 当前任务上下文与中间状态 | Prompt、状态对象 |
| 会话记忆 | 当前对话中的重要事实 | 摘要、消息历史 |
| 长期记忆 | 跨会话偏好与稳定事实 | 数据库、向量库 |
| 程序性记忆 | 工作流程和规则 | 代码、Prompt、技能定义 |

写入长期记忆前要考虑正确性、隐私、过期时间和用户可控性。模型一次推测不能自动变成永久事实。

## 9. 技术方案的选择顺序

面对“让模型回答得更好”的需求，可按以下顺序判断：

```text
输出格式或指令理解问题
→ 先改 Prompt 与结构化约束

需要最新、私有、可引用知识
→ 优先 RAG 或工具查询

需要稳定学习特定行为和风格
→ 评估 SFT / LoRA

需要执行外部动作
→ Tool Calling + 权限控制

需要多步自主完成任务
→ 在工具层之上增加受控 Agent

基础模型能力明显不足
→ 更强模型、领域继续预训练或更大规模训练
```

不要用微调解决所有知识更新问题，也不要用 Agent 包装一个单次调用即可完成的任务。

## 10. 三条后续深入路线

**模型与训练路线**

```text
Tokenizer
→ Transformer 变体
→ 数据治理
→ 分布式预训练
→ SFT 与偏好优化
→ 评估与对齐
```

**推理系统路线**

```text
生成算法
→ KV Cache
→ 高效 Attention
→ 量化
→ 批处理与调度
→ 多 GPU 服务
→ 性能工程
```

**应用工程路线**

```text
Prompt 与结构化输出
→ RAG
→ Tool Calling
→ Memory
→ Agent
→ 评估、安全与可观测性
```

三条路线共享 Tokenizer、Transformer 数据流、推理与评估基础，不需要一开始同时深入。

## 11. 应用系统的统一评估框架

任何方向都应至少评估：

| 维度 | 示例问题 |
|---|---|
| 正确性 | 结果是否满足任务定义 |
| 可靠性 | 多次运行和异常输入是否稳定 |
| 可追溯性 | 能否定位数据、模型、工具和证据来源 |
| 安全性 | 是否越权、泄密或执行危险动作 |
| 性能 | 延迟、吞吐、显存和成本是否满足目标 |
| 可维护性 | 配置、日志、测试和版本是否清楚 |

离线测试集、线上指标和人工评审应互相补充。

## 12. 本章验收

- 能区分预训练、继续预训练、SFT 与偏好优化。
- 能用低秩增量解释 LoRA 的参数节省。
- 能说明 QLoRA 降低的主要是基础权重存储。
- 能画出 RAG 的检索、重排、生成与引用链路。
- 能说明模型提出工具调用不等于获得执行权限。
- 能把 Agent 描述为有停止条件的状态循环。
- 能根据需求选择 Prompt、RAG、LoRA、Tool 或 Agent。
- 能选择一条后续深入路线并说明理由。
