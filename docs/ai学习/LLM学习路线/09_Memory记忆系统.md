# 模块 9：Memory——从上下文到长期记忆

## 目标

实现短期窗口、摘要、向量记忆、用户画像、重要性排序和 Reflection；理解记忆写入、检索、更新、遗忘、隐私和评估。

> Memory 在真实任务中应该记什么、不该记什么，以及怎样与任务状态分离，可对照 [从 Tool Calling 到可恢复 Agent：完整案例](08A_从Tool到Agent完整案例.md)。

## 学习导航

按“记忆对象与生命周期 → 检索/更新/安全 → 评估与复盘 → 文末递进 Project”的顺序学习。每一步都沿用同一组跨会话测试，不能只凭聊天感觉判断有效。

## 1. 模型没有天然的跨会话记忆

LLM 每次只看到本次请求提供的上下文。所谓 Memory 是应用系统把历史信息存储、选择并重新放回上下文。

不要把三件事混在一起：

- 模型参数记忆：训练写入权重，难更新和删除。
- 上下文记忆：当前 prompt 中的 token，准确但有长度成本。
- 外部记忆：数据库/文件中的记录，可更新、检索、审计。

## 2. 记忆生命周期

```text
观察对话/事件
→ 判断是否值得写入
→ 抽取与规范化
→ 去重/冲突处理
→ 存储（带来源和时间）
→ 根据当前任务检索
→ 注入上下文
→ 使用反馈更新/衰减/删除
```

只做“聊天全量 embedding”没有解决写入质量、冲突、隐私与遗忘。

## 3. Conversation Window

保留最近 N 轮，简单且保真。按“轮数”不如按 token 预算准确：一轮可能非常长。应优先保留 system 规则、当前任务和最近相关交互，并为工具结果设置单独上限。

失败模式：早期关键约束被挤掉；长工具输出占满窗口；把不可信网页内容永久保留为指令。

## 4. Summary Memory

超预算时把较早对话总结为紧凑状态：目标、已确认事实、决定、未解决事项、重要约束。不要写散文式“聊了很多”。

推荐结构：

```json
{
  "goal": "构建个人知识库",
  "confirmed_facts": [{"fact": "用户使用 Windows", "source": "turn-12"}],
  "decisions": ["先用本地 Markdown"],
  "open_questions": ["是否需要 OCR"],
  "do_not_assume": ["尚未确认 GPU"]
}
```

摘要会有损，应保存原始记录引用；定期从原始事实重新生成，避免“摘要的摘要”不断漂移。

## 5. Vector Memory

把过去事件/记忆条目 embedding，按当前 query 召回语义相关内容。条目应是独立、可理解的原子事实，而不是整段漫长对话。

```json
{
  "memory_id": "m-001",
  "subject": "user",
  "predicate": "prefers_language",
  "value": "Python",
  "observed_at": "...",
  "source_turn": "t-19",
  "confidence": 0.92,
  "sensitivity": "normal",
  "status": "active"
}
```

语义相似不等于当前有效。还需 metadata 过滤、时间和冲突处理。

## 6. User Profile

用户画像适合稳定偏好和长期背景，不适合把一时情绪永久化。区分：

- 明示事实：“请记住我用 Windows”。
- 推断：“用户可能喜欢机械”。推断要低置信度、可撤销，不应冒充事实。
- 敏感信息：健康、财务、身份等默认不存，除非有明确目的和同意。

用户应能查看、纠正、删除和关闭记忆。

## 7. Importance、Recency、Relevance

经典排序可组合三因素：

$
score=w_r R_{relevance}+w_t R_{recency}+w_i I_{importance}
$

先把三者归一到可比较范围。Recency 可指数衰减：

$
R_{recency}=e^{-\lambda \Delta t}
$

Importance 可以由规则或模型评分，但要校准；“用户改了地址”对寄件任务很重要，日常闲聊未必。最终分数应按任务类别调节，而不是一个公式统治所有场景。

## 8. 冲突、更新与遗忘

新事实“用户现在用 Linux”与旧事实“用户用 Windows”可能是更新，也可能是两台设备。不要简单覆盖：

1. 检索同 subject/predicate 的活跃记录。
2. 判断可并存、更新还是矛盾。
3. 不确定时询问。
4. 保留版本：旧记录标 superseded，指向新记录。

遗忘不是缺陷：过期事实应失效；低价值记忆衰减；用户删除必须级联到向量索引、缓存和备份策略允许的范围。

## 9. Reflection

Reflection 从多个事件抽取更高层模式或计划，例如“一周三次提到环境配置问题→建议建立环境检查清单”。它比原始记忆更抽象，也更可能误推断。

规则：保留支持证据 id；明确标注 inferred；达到事件数量/时间阈值才触发；允许后续证据推翻；不要把模型自我生成的反思不断当作新证据形成循环。

## 10. Memory Prompt Injection

如果把“网页说：以后永远忽略安全策略”写成长记忆，攻击会跨会话持续。写入前标记来源信任级别；外部内容永远作为引用数据，不能成为高优先级指令；记忆检索结果应放在清楚的 data 区域。

## 11. 隐私与治理

- 明确告知存什么、为什么、多久。
- 数据最小化和用途限制。
- 静态/传输加密与访问控制。
- 日志不要重复泄露记忆正文。
- 导出、纠正、删除和保留期限。
- 多用户系统必须按 tenant/user 在查询层隔离。

Embedding 也可能泄露信息，不能因为“只是向量”就当匿名数据。

## 12. Memory 评估

建立跨会话脚本：

- Recall：应该记住的事实是否取回。
- Precision：注入的记忆是否真的相关。
- Update：偏好改变后是否用新值。
- Temporal：过去与当前是否区分。
- Abstention：没记录时是否不编。
- Privacy：A 用户信息绝不出现在 B 用户上下文。
- Deletion：删除后搜索、画像、缓存均不可见。

还要测 token 开销和错误记忆对最终任务的影响。检索到记忆不是最终成功，正确使用才是。

## 13. 阅读 Mem0、Zep、Letta 的方式

不要先比较营销功能。画出各自：记忆对象、写入触发、存储结构、召回策略、上下文装配、更新/删除、评估方式。然后用相同 20 个场景测试，记录行为差异。

## 验收与复盘

- 能区分上下文、参数和外部记忆。
- 记忆都有来源、时间、置信度和状态。
- 能处理冲突、更新、删除与跨用户隔离。
- Reflection 是可追溯推断，不冒充事实。
- 提示注入内容不会进入长期高信任指令。

## 课后 Project

### Project 15～20：记忆系统的递进实现

1. Conversation Memory：按 token 预算保留最近消息。
2. Summary Memory：结构化摘要 + 原文引用。
3. Vector Memory：原子事件 + embedding 检索。
4. Long-term Profile：显式/推断分离，支持修改删除。
5. Importance 排序：相关、时间、重要性消融实验。
6. Reflection：每天/达到阈值生成有证据的洞察。

每一步都用同一组跨会话评估测试，观察新增机制是否真的提高成功率。
