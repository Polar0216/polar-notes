    流媒体¶

    整体流程¶

    先看一个最简单的流程：

    网页

    ↓

    HTML

    ↓

    JavaScript

    ↓

    向服务器请求歌曲信息(API)

    ↓

    服务器返回歌曲URL

    ↓

    浏览器请求音频文件

    ↓

    服务器返回音频字节流

    ↓

    浏览器播放

    第一步：浏览器打开网页¶

    例如你打开

    https://music.xxx.com/song?id=123

    浏览器第一件事：

    GET /

    服务器返回

    index.html

    里面可能只有

    HTML

    几乎没有内容。

    第二步：JS请求歌曲信息¶

    例如

    GET /api/song?id=123

    服务器返回

    JSON

    {

    "name":"xxx",

    "artist":"yyy",

    "cover":"...",

    "audio":"https://cdn.xxx.com/abcdef.mp3"

    }

    注意：

    很多人误以为

    HTML里面就有MP3

    实际上根本没有。

    真正是在JS拿到JSON以后：

    JavaScript

    audio.src = json.audio;

    或者

    JavaScript

    new Audio(json.audio)

    浏览器这时候才知道

    哦，

    真正的音频地址是

    https://cdn.xxx.com/abcdef.mp3

    第三步：浏览器开始下载MP3¶

    浏览器看到

    src=

    以后：

    自动发HTTP请求。

    例如

    GET /abcdef.mp3

    服务器：

    200

    OK

    Content-Type: audio/mpeg

    下面开始疯狂传二进制：

    111000101010...

    其实就是MP3文件。

    浏览器：

    一边收

    一边解码

    一边播放。

    所以：

    浏览器播放音乐，本质就是不断接收字节流。

    第四步：为什么Network里面能看到¶

    其实Network就是：

    浏览器自己的收支账本。

    浏览器每发一个HTTP请求：

    都会记下来。

    例如：

    index.html

    main.js

    style.css

    logo.png

    cover.jpg

    abcdef.mp3

    所以你看到：

    Media里面：

    abcdef.mp3

    不是Chrome帮你找到的。

    而是：

    Chrome自己刚刚下载的。

    开发者工具只是把它显示出来。

    第五步：为什么复制URL还能下载¶

    因为：

    https://cdn.xxx.com/abcdef.mp3

    本来就是服务器给浏览器的。

    浏览器也是：

    GET

    你复制URL以后：

    浏览器会尝试发起一次新的请求，但如果缓存有效，可能直接从本地读取

    如果浏览器又发了一遍：

    GET

    服务器：

    200

    于是下载。

    补充一：为什么有的网站复制URL就失效¶

    这就是很多视频网站开始做的事情。

    例如：

    https://cdn.xxx.com/abcdef.mp3?token=xxxxx

    里面有：

    token

    可能：

    一分钟以后：

    403

    因为：

    Token过期。

    例如：

    Expires

    Signature

    Policy

    AuthKey

    都是这个意思。

    这样别人复制URL：

    打不开。

    补充二：Cookie什么作用¶

    注意：若音频在CDN跨域域名下，默认不会携带主站Cookie，此时主要依赖URL签名防盗链

    浏览器请求：

    GET song.mp3

    实际上还会带：

    Cookie

    例如：

    Cookie:

    login=true

    VIP=yes

    session=xxxxx

    服务器收到：

    哦，这个账号是会员，可以播放。

    否则：403或者VIP only

    补充三：为什么有时候直接打开URL还是能下载¶

    因为：很多CDN只验证第一次API。

    例如：

    API：

    是不是会员？

    ↓

    返回URL

    ↓

    CDN：

    谁拿URL都能下载。

    因为：

    CDN压力小。

    速度快。

    所以：

    浏览器拿到URL以后任何人复制都能下载。

    这是很多网站以前的做法。

    现在越来越少。

    补充四：DRM是什么¶

    Netflix

    Disney+

    Apple TV+

    Spotify（部分内容）

    他们即使下载audio.mp4

    里面也是加密数据。

    浏览器拿到AES加密后的数据

    浏览器里面有：

    Widevine

    PlayReady

    FairPlay

    这些DRM模块。

    它们向授权服务器申请密钥

    例如：

    License Server

    服务器检查：

    是不是会员？

    是，返回加密的License许可证，由底层DRM模块在安全环境中解码

    浏览器内存里解密播放

    注意：

    真正的密钥通常不会以普通 JavaScript 可直接读取的形式暴露给网页代码，而是由浏览器或操作系统中的 DRM 模块处理。

    所以即使你在 Network 里看到的是：

    audio.mp4

    你下载下来也是：乱码。

    理论上如果内容最终要给人听/看一定存在解密后的数据

    因为扬声器需要声音，屏幕需要画面。

    所以从纯理论角度：

    "只要人能看到，就一定存在某个时间点的数据。"

    这就是所谓：

    模拟漏洞（analog hole）

    比如：

    你拿手机拍屏幕。

    技术上无法完全消灭。

    但是 DRM 的目标不是数学意义上的：

    绝对防止复制。

    而是提高成本。

    让：

    普通用户：

    下载文件

    → 打开

    → 上传

    变困难。

    补充五：切成小段¶

    现代流媒体视频通常会被切成很多小片段（Segment），这些片段通常对应几秒钟的播放时间， 然后按需下载

    假设有一个 60 分钟的视频。

    服务器不会存成：

    movie.mp4

    而可能存成：

    0~4 秒

    ↓

    0001.m4s

    4~8 秒

    ↓

    0002.m4s

    8~12 秒

    ↓

    0003.m4s

    ...

    3596~3600 秒

    ↓

    0900.m4s

    每个片段：

    • 2 秒

    • 4 秒

    • 6 秒

    • 10 秒

    都有可能，不同平台不同。

    播放器播放的时候就是：

    下载0001

    ↓

    开始播放0001

    ↓

    后台下载0002

    ↓

    播放0002

    ↓

    后台下载0003

    所以网络一直都在工作。

    那为什么还能快进？¶

    假设你突然拖到：

    45:20

    播放器不会：

    重新下载前45分钟

    播放器能精准快进，靠的不是自己算时间，而是提前下载的 .m3u8 或 .mpd 索引清单文件，里面 记录了每个分片对应的实际时间轴

    45:20

    ↓

    对应第680段

    ↓

    请求680.m4s

    所以几乎立刻就能播放。

    那画质为什么可以切换？¶

    因为：

    服务器其实准备了很多套片段。

    例如：

    360P

    0001

    0002

    0003

    720P

    0001

    0002

    0003

    1080P

    0001

    0002

    0003

    假设现在已经播放到：

    第100段

    突然网速变慢。

    播放器就改成：

    不要1080P第101段

    改下720P第101段

    这样用户几乎感觉不到，这就是自适应码率（Adaptive Bitrate, ABR）。

    那音频为什么很多时候不是这样？¶

    那音频为什么不常看到切片（m4s）文件？¶

    其实在现代正版流媒体（Spotify、Apple Music、YouTube Music）中，音频同样被切成小段（HLS/DASH）。你去Network里翻，看到的全是segment_001.m4s、segment_002.m4s。

    切片对音频有三个巨大的好处： 1. DRM加密更安全：每个小片段独立加密，密钥随时轮换，防盗版能力远强于加密整个MP3。 2. 自适应码率（ABR）：信号不好时切128kbps，5G满格切无损FLAC，切片是实现这种无缝切换的基础。 3. 无缝播放（Gapless）：切片格式（如init.mp4+m4s）天生支持歌曲间无间隙播放，整首MP3拼接时容易产生爆音。

    那为什么我们印象里音频不切片呢？ 因为切片通常在播放器底层自动发生，用户完全无感知。而且有些独立音乐人网站、老式播客、或者技术演示Demo，确实还在用整首MP3（因为实现起来最傻瓜，不需要搭建HLS服务器）。 所以真相是：

    大厂音乐现在基本都是切片，只有简单网页播放器或老式站点才直接丢一个完整的MP3。
